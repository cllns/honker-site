---
title: Ruby ORM integration
description: Use Honker from Rails/ActiveRecord, Sequel, Rom, or Hanami by loading the SQLite extension and wrapping honker_* SQL calls.
---

Rails and ActiveRecord can load SQLite extensions through the sqlite3 gem configuration. Sequel loads them through an `after_connect` hook, and Rom (built on Sequel) and Hanami (built on Rom) do the same. Once loaded, Honker calls are ordinary SQL inside the database's transaction.

## ActiveRecord (Rails)

As of the `sqlite3` gem 2.4+ and [Rails PR #53827](https://github.com/rails/rails/pull/53827), extensions are declared in `config/database.yml`:

### Wiring

```yaml
default: &default
  adapter: sqlite3
  pool: <%= ENV.fetch("RAILS_MAX_THREADS") { 5 } %>
  timeout: 5000
  extensions:
    - /path/to/libhonker_ext

development:
  <<: *default
  database: storage/app.db
```

Run `SELECT honker_bootstrap()` once from an initializer or migration:

```ruby
# config/initializers/honker.rb
Rails.application.config.after_initialize do
  ActiveRecord::Base.connection.execute("SELECT honker_bootstrap()")
end
```

### Wrapper

```ruby
# app/lib/honker.rb
module Honker
  def self.enqueue(queue, payload, delay: nil, priority: 0, max_attempts: 3)
    sql = ActiveRecord::Base.sanitize_sql_array([
      "SELECT honker_enqueue(?, ?, NULL, ?, ?, ?, NULL) AS id",
      queue, payload.to_json, delay, priority, max_attempts
    ])
    ActiveRecord::Base.connection.select_value(sql)
  end

  def self.notify(channel, payload)
    sql = ActiveRecord::Base.sanitize_sql_array([
      "SELECT notify(?, ?)",
      channel, payload.to_json
    ])
    ActiveRecord::Base.connection.execute(sql)
  end
end
```

### Usage

```ruby
ActiveRecord::Base.transaction do
  Order.create!(user_id: 42)
  Honker.enqueue("emails", { to: "alice@example.com" })
  Honker.notify("orders", { id: 42 })
end
```

Workers run as a separate process using the [`honker` Ruby gem](https://rubygems.org/gems/honker).

## Sequel

Sequel loads SQLite extensions through an `after_connect` hook on `Sequel.connect`. Once the extension is loaded, `honker_*` functions are callable through Sequel's normal query API.

### Wiring

```ruby
# config/db.rb
require "sequel"

EXT_PATH = ENV.fetch("HONKER_EXTENSION_PATH", "/path/to/libhonker_ext")

DB = Sequel.connect(
  "sqlite://storage/app.db",
  after_connect: proc do |conn|
    conn.enable_load_extension(true)
    conn.load_extension(EXT_PATH)
    conn.enable_load_extension(false)
  end,
)

DB.run("SELECT honker_bootstrap()")
```

Storing the connection in a top-level `DB` constant is Sequel's recommended convention: `Sequel::Model` classes and the `Honker` wrapper below both resolve it from there, so the whole process shares one connection pool.

`honker_bootstrap` is idempotent — safe on every connect in development; move it to a one-time migration or boot hook in production.

### Wrapper

```ruby
# lib/honker.rb
module Honker
  def self.enqueue(queue, payload, delay: nil, priority: 0, max_attempts: 3)
    DB.get(
      Sequel.function(
        :honker_enqueue,
        queue, payload.to_json, nil, delay, priority, max_attempts, nil,
      ),
    )
  end

  def self.notify(channel, payload)
    DB.get(Sequel.function(:notify, channel, payload.to_json))
  end
end
```

`Sequel.function` binds arguments through Sequel's expression layer, so payloads and channel names are parameterized rather than interpolated. `DB.get(expr)` runs `SELECT expr` and returns the single scalar result.

### Usage

`Order` is an ordinary `Sequel::Model` that resolves the `DB` constant automatically. Wrap the model write and the Honker calls in `DB.transaction` so they commit — or roll back — together:

```ruby
DB.transaction do
  Order.create(user_id: 42, total: 9900)
  Honker.enqueue("emails", { to: "alice@example.com" })
  Honker.notify("orders", { id: 42 })
end
```

## Rom (with ROM::SQL)

[rom-sql](https://hanakai.org/rom) is built on Sequel, so the Honker integration is nearly identical to the [Sequel recipe above](#sequel) — the same `after_connect` extension load and the same `Sequel.function` calls. Rom forwards connection options straight through to `Sequel.connect`.

Pass the connection string and `after_connect` straight to `ROM.container`; rom-sql forwards them to `Sequel.connect`. Running `honker_bootstrap` inside `after_connect` makes sure `_honker_live` exists before Rom infers relation schemas:

```ruby
rom = ROM.container(:sql, "sqlite://storage/app.db",
  after_connect: proc do |conn|
    conn.enable_load_extension(true)
    conn.load_extension(EXT_PATH)
    conn.enable_load_extension(false)
    conn.execute("SELECT honker_bootstrap()") # idempotent; can also live in a migration
  end,
) do |config|
  config.relation(:honker) { schema(:_honker_live, infer: true) }
  # ... your other relations
end
```

If you'd rather keep connection setup separate, build the `Sequel::Database` yourself, run `honker_bootstrap` on it, then hand the object to `ROM.container(:sql, sequel_db)`. Just make sure the bootstrap runs before the container is built, since schema inference reads `_honker_live` at that point.

The `:honker` relation points at Honker's internal queue table only so the wrapper has a connection to reach — you never query it for business logic. A repository is the natural home for the same `Sequel.function` call the Sequel recipe uses:

```ruby
class HonkerRepo < ROM::Repository[:honker]
  def enqueue(queue, payload, delay: nil, priority: 0, max_attempts: 3)
    honker.dataset.db.get(
      Sequel.function(
        :honker_enqueue,
        queue, payload.to_json, nil, delay, priority, max_attempts, nil,
      ),
    )
  end

  def notify(channel, payload)
    honker.dataset.db.get(
      Sequel.function(:notify, channel, payload.to_json),
    )
  end
end
```

Transactions still go through Sequel — Rom commands and the Honker calls share the connection, so an exception inside the block rolls back the business write and the enqueue together.

### Alternative: a custom command

If you'd rather the enqueue look like a first-class Rom operation, register a custom command instead of a repository method. Subclass `ROM::SQL::Commands::Create`, point it at the `:honker` relation, and override `execute`:

```ruby
class EnqueueCommand < ROM::SQL::Commands::Create
  relation :honker
  register_as :enqueue
  result :one

  def execute(tuple)
    id = relation.dataset.db.get(
      Sequel.function(
        :honker_enqueue,
        tuple.fetch(:queue), tuple.fetch(:payload).to_json,
        nil, nil, 0, 3, nil,
      ),
    )
    [{ id: id }]
  end
end
```

Register it in the container block, then call it through `rom.commands`:

```ruby
rom = ROM.container(:sql, sequel_db) do |config|
  config.relation(:honker) { schema(:_honker_live, infer: true) }
  config.register_command(EnqueueCommand)
end

rom.commands[:honker][:enqueue].call(queue: "emails", payload: { to: "alice@example.com" })
# => {id: 1}
```

The friction: the command machinery is tuple-shaped. `execute` must return an *array of tuples*, so the scalar id gets wrapped as `[{ id: id }]` for `result :one` to unwrap. For a single SQL function call returning one value, the repository method above is the simpler fit — the command is worth it mainly for encapsulation: a named, registered component on equal footing with the rest of your command layer, testable in isolation. (As an aside, that also makes it composable with ROM's `>>` operator, though a side-effecting function call rarely benefits.)

### Doing it from a dry-operation

You most likely want the enqueue at the repo level, as shown above. But sometimes you want to enqueue a job or fire a notification ad-hoc, right where one particular workflow calls for it. If your app uses [`dry-operation`](https://rubygems.org/gems/dry-operation), that fits naturally inside the operation itself.

The ROM extension adds a `transaction` method that wraps the enclosed steps in a Rom transaction and rolls back automatically if any step returns a `Failure`:

```ruby
class PlaceOrder < Dry::Operation
  include Deps["repos.orders_repo", "repos.honker_repo"]

  # include Dry::Operation::Extensions::ROM

  def call(input)
    transaction do
      order = step orders_repo.create(input)
      honker_repo.enqueue("emails", { to: input[:email], order_id: order.id })
      order
    end
  end
end
```

In a Hanami app that is the whole operation: Hanami requires `dry/operation/extensions/rom` and includes `Dry::Operation::Extensions::ROM` for you, and injects `rom` from the slice. Outside Hanami, add `require "dry/operation/extensions/rom"` and uncomment the `include` (that extension is what defines `transaction`), plus supply a `#rom` method returning the Rom container.

The `honker_enqueue` call still lives in a repo (or wrapper); the operation only adds orchestration and the rollback-on-`Failure` boundary.

### Hanami

Hanami's `hanami-db` is built on ROM::SQL, so the recipe above carries over. The extension load just moves into Hanami's database provider:

```ruby
# config/providers/db.rb
Hanami.app.configure_provider(:db) do
  config.gateway(:default) do |gateway|
    gateway.connection_options(
      after_connect: proc do |conn|
        conn.enable_load_extension(true)
        conn.load_extension(ENV.fetch("HONKER_EXTENSION_PATH"))
        conn.enable_load_extension(false)
      end,
    )
  end
end
```

The relation and repo are the same as above, written as Hanami classes:

```ruby
# app/relations/honker.rb
module YourApp
  module Relations
    class Honker < Hanami::DB::Relation
      schema(:_honker_live, as: :honker, infer: true)
    end
  end
end
```

```ruby
# app/repos/honker_repo.rb
module YourApp
  module Repos
    class HonkerRepo < Hanami::DB::Repo
      # enqueue / notify exactly as in the Rom recipe above
    end
  end
end
```

Prefer the [custom command](#alternative-a-custom-command)? Put the same class in `app/db/commands/` and Hanami registers it automatically.
